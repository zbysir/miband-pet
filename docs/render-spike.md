# 动态渲染实验

插件基座最初的想法是：手环上只装一个通用的「渲染器」快应用，插件逻辑都在 Mac 上跑，Mac 把界面树发给手环画，手环把点击、滑动传回 Mac。这份文档记录在真机（小米手环 10 Pro，屏幕 336×480）上验证这条路能不能走通的结果。

实验代码：手环端 `spike/render-app/`，Mac 端 `server/cmd/spike/`。

> 后来通用渲染器（`render-app/`）和 JSX 插件都换掉了：每个 app 用快应用原生的 `.ux` 写，Mac 上编译成独立的快应用装到手环上（见 [apps.md](apps.md)），原因见下面「小米手环 9 Pro 上的问题」和耗时对比。这份文档留着手环上实测的数据（消息大小、节点创建速度、JS 引擎能力、9 Pro 的坑），下文提到的 `render-app/`、`index.ux` 的 `patch` 等代码已经删了，在 git 历史里。

## 结论先说

**能走通。** 整串 style 动态绑定、4 层嵌套、运行时推送的图片和逐帧动画都能用，点一下到画出新界面只要 50ms 左右。后来又发现手环能执行 Mac 推过去的代码，最后插件改成在手环上跑（见「手环能执行动态下发的代码」）。

要注意的有三点：

1. **单条消息不要超过 16KB。** 发 64KB 的消息会让手环不再确认数据帧，连接卡死，只能断开重连。
2. **新建节点很慢，改已有节点很快。** 新建大约每个节点 10ms，结构不变只改属性只要 40ms 左右。渲染器要尽量保持界面结构稳定，长列表要分页。
3. **渲染刚开始时调 `getBoundingClientRect` 可能永远没有回调**，要每隔几十毫秒重试。

## 结果

### 整串 style 动态绑定：可以

模板里写 `style="{{node.style}}"`，`node.style` 是 Mac 发来的一整串 CSS（如 `flex-direction:row;padding:4px;width:180px`），手环会照着排版。量出来的布局和 CSS 预期一致（14 项全过）：padding、margin、宽高、`flex-direction`、`justify-content: space-between`。

换一串新的 style，手环也会重新排版（3 项全过）。

`getBoundingClientRect` 返回的是物理像素，按 `屏幕宽 / designWidth`（336/212）换算。

### 任意嵌套：两种做法都可以

- **递归组件**（`spike/render-app/src/components/rnode.ux` 在模板里引用自己）：能编译，能渲染，布局正确。但官方文档说自定义组件「有独立的 ViewModel，存在一定内存开销，在手表手环等轻量级设备上不建议使用」，实测也比较慢（见下面性能）。
- **页面模板里写死 4 层**：每层用 `for` 遍历子节点，按 `type` 用 `if/elif` 选 `div`、`text`、`image`、`image-animator`。不用自定义组件，嵌套层数有上限。

正式做基座建议选写死层数，层数可以多写几层。

### 运行时推送图片：可以

Mac 把 PNG 用 base64 发过去，手环解码后用 `file.writeArrayBuffer` 写到 `internal://files/xxx.png`，`<image src="internal://files/xxx.png">` 能正常显示，也会触发 `complete` 事件。`image-animator` 的帧也可以是 `internal://` 路径，动画正常播放。

一张 180 字节的小图，从推送到写好约 70ms。

### 消息大小和速度

| 消息大小 | 耗时 | 速度 |
|---|---|---|
| 512 B | 40~60 ms | — |
| 2 KB | 47 ms | 约 43 KB/s |
| 8 KB | 120 ms | 约 65 KB/s |
| 16 KB | 170~210 ms | 约 80~95 KB/s |
| 32 KB | 320~350 ms | 约 90~100 KB/s |
| 64 KB | 连接卡死 | — |

### 性能

新建一棵树，从手环收到消息到能量到最后一个节点：

| 节点数 | 写死层数 | 递归组件 |
|---|---|---|
| 31 | 0.37 秒 | 0.58 秒 |
| 91 | 0.96 秒 | 1.2 秒 |
| 181 | 1.9 秒 | 2.5 秒 |

结构不变、只改文字和宽度（手环发 ping → Mac 回新树 → 手环画完）：中位 **43ms**，P90 94ms。第一轮要把上一个测试的大树换成小树，用了 2.2 秒。

**点按延迟**：手指点下 → 手环把事件发给 Mac → Mac 回新树 → 手环画完，24 次在 32~91ms 之间，大多在 40~55ms。

### 手环能执行动态下发的代码：可以

这是后来补的实验（`go run ./cmd/spike -evaltest`）：Mac 发一段代码字符串，渲染器用 `new Function` / `eval` 执行。结果都能用，语法支持到 ES2020：

| 测什么 | 结果 |
|---|---|
| `new Function`、`eval` | 可以 |
| 箭头函数、`let/const`、模板字符串、解构、展开、默认参数 | 可以 |
| `class`、`Map`、`Set`、`for...of`、`Proxy`、`Symbol` | 可以 |
| 可选链 `?.`、空值合并 `??`（ES2020）、`async/await` | 可以 |
| 全局 `setTimeout` / `setInterval` | 有 |
| 10 万次循环 + 1000 个对象 `JSON.stringify` | 312ms（比 Mac 慢上百倍） |

所以插件不用在 Mac 上跑：Mac 编译好推过去，插件在手环本地跑，点击不用走蓝牙往返。

## 对基座设计的影响

- 插件在手环上跑（见上一节），Mac 只推代码、图片和数据。
- 节点 id 要稳定，结构不变时手环只更新属性；结构变了也尽量复用已有节点。
- 每条消息控制在 16KB 以内，代码和图片分片发送，按内容哈希命名，推过就不再推。
- 一屏的节点数控制在几十个以内，长列表分页。
- 动画在手环本地播，不要靠 Mac 一帧帧推。现在不用 `image-animator`，由页面定时换 `image` 的图片（见下一节）。

## 小米手环 9 Pro 上的问题

在 9 Pro（`device.getInfo` 的 `product` 是 `Xiaomi Smart Band 9 Pro`，平台版本 1.2.0）上测出来的，10 Pro 上没有。渲染器里都绕开了：

1. **页面开着时拆掉一个 `image-animator`，整个手环会重启。** 换动画、切插件、动画所在的那段节点重建都会拆。页面整个退出时拆不会。所以 `Sprite` 不用 `image-animator`，画成普通 `image`，页面定时换 `src`（`index.ux` 的 `startSprites`）。代价是动画要靠 JS 计时器，JS 忙的时候（收到数据重算界面）会顿一下。
   - 后来改成原生 `.ux` 之后在 9 Pro 上重新试过：用 `if` 拆掉再装回 `image-animator`、连着换十几次帧列表，都不会重启，所以重启应该是通用渲染器那套写法引起的。现在 Agent 猫的动画用的就是 `image-animator`。另外实测它的 `duration` 是**每帧**停多久，不是一轮的时长；换了帧列表要等约 300ms 再 `start()`。
2. **快应用刚连上时发的消息会丢**，发送失败的错误是 `{"data":"not connected","code":401}`。手环发给 Mac 的 hello 丢了，Mac 就以为快应用没开，什么都不推。现在 hello 没等到 Mac 回应就每秒重发，最多 10 次；发送失败的记录等 Mac 有回应后发过去记日志。
3. **改了已经画出来的元素的样式，之后别处的文字一变，排版就乱**：元素挤到页面顶上，重新打开页面才好。只改文字、只改样式都不会，同一个文字节点的文字和颜色一起改也不会。原因是通用模板的 `style` 绑的是整串（宽高、边距、flex 全在里面），任何一项变了框架就把整串重设一遍，排版属性也重设了；原生写法把排版属性写在 class 里、只绑颜色，就没事。现在 9 Pro 上文字（`text`）只变了颜色时，只把变了的几项写进绑定的样式串（`index.ux` 的 `styleDelta`），排版属性不动；其它情况把这个元素重建（换模板里的 `tid`）。容器（`div`）不能这样改：绑定的样式换成只有变了的几项后，`div` 原来的样式会被整个顶掉，比如气泡只换了边框色，宽高、底色、竖排就都没了，框不见、里面的字横着挤在一起，一直到这个元素被重建。所以 `div` 的样式一变就重建。
   - 重建一个元素时，框架要把它所在的那整层子节点列表重新比一遍，猫页最外层一层要 500ms 以上。所以模板里每个子节点外面套了一层只装它自己的列表（「槽」，`block` 不产生元素），重建时只换这个槽，约 30ms 一个元素。

9 Pro 上的耗时（点一下到交给框架，再到框架处理完）：

| 操作 | 插件（优化前） | 插件（现在） | 同样界面用原生 `.ux` 手写 |
|---|---|---|---|
| 猫页点气泡 | 约 240ms（JS 约 200ms，框架约 40ms） | 约 110ms（JS 约 80ms，框架约 30ms） | 约 30ms |
| 今日页切小鱼干 / 钱数 | 约 500ms（JS 约 320ms，框架约 175ms） | 约 440ms（JS 约 270ms，框架约 170ms） | 约 270ms |

插件慢在 JS：插件组件重算、转成界面树、拼样式串、页面比较新旧两棵树，原生写法这些都没有。降下来靠的是：

- 运行时：组件重算后每个节点和上次同一个 id 的比，没变的交出上次的对象（页面整棵子树跳过不比）；上层组件只是把上次的元素重新展开时，下面没有要重算组件的容器直接用上次展开好的节点；Row / Col 这类容器不登记组件实例。
- 插件：把常变的状态放进小组件（Agent 猫点气泡只重算气泡）。

在 Mac 上可以用 QuickJS（`brew install quickjs`，和手环同一种引擎）估算：Mac 上大约是手环的 1/550。

另外：页面上改节点（比如动画换帧）要从 `this.root` 往下找到节点再改；直接改页面自己记下的同一个对象，界面不会变（见 `index.ux` 的 `startSprite`）。
